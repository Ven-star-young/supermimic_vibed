# CUHK visit 27 CUDA OOM 诊断与修复

2026-10-27，原正式训练采用两张A100 40GB、每卡512环境、WM/Actor batch256，
在第1350次迭代后的场景切换报错：

```text
[multi-chair rank=1] visit=27 scene=51/151 covered=28/151
Warp CUDA error 2: out of memory (in function wp_cuda_graph_launch, ...)
```

rank1显存40,415 MiB，rank0仍在等待集合通信；600秒后NCCL watchdog超时，
torchrun结束整组进程。NCCL超时是后果，最先发生的是Warp显存不足。原运行未到2000次
保存间隔，没有可恢复checkpoint；没有人工中止或重启这轮正式训练。

## 可重复证据

失败资产是 `sitting__druidic_stone_seat_ancient_ritual_carved_granite__000.npz`，
完整场景含1431个geom、713个mesh。初始qpos0检测到1574接触、6296约束，其中1351条
接触是椅子与地面。该默认姿态在参考reset之前，不代表正常坐下时的接触数。

早期容量策略按初始数量乘2、再向上取2的幂，分配4096接触/16384约束。新进程在空闲
GPU上仅运行该场景的512个物理环境、完全没有学习网络，就占约36.7 GiB设备显存；
因此无需假设训练网络泄漏，也能解释正式训练加载网络后OOM。

控制实验保持模型默认姿态、碰撞几何、512环境和动作不变，仅改为2048/8192容量，
设备显存降到约18.9 GiB，连续重建两轮没有继续增长，实际约束最大约2552，未出现溢出。
另一个仅抬高默认位姿的实验虽然降低显存，却使容量过低并触发NEFC溢出，因此未采用。

## 实现

实体场景仍先用CPU模型测量初始需求，但改为25%余量，接触按128、约束按512对齐。
保留每物体512/2000的下限和用户显式指定的更大容量。这样避免了“乘2再取2的幂”
接近4倍扩容，以及容量门槛附近的显存突增。没有修改碰撞网格、奖励、参考数据或网络。

Replay在真实step之后、记录转移与episode reset之前检查Warp的累积overflow位掩码，
发现接触、约束等溢出即抛出明确错误，避免将截断物理状态用于训练。标记跨子步保留，
所以后续子步接触减少不会掩盖此前的溢出。这不是CUDA OOM恢复或紧急保存机制。

诊断工具同时记录PyTorch峰值和checkpoint时整个设备的已用显存；后者包含Warp、
CUDA graph及NCCL分配。只看 `torch.cuda.max_memory_allocated()` 会严重低估这次问题。

## 验证

扫描全部151种训练场景的CPU初始接触/约束需求，最大两种为ball pod chair和pumpkin
chair，分别1774/7096和1742/6968。旧分配均为4096/16384，新分配均为2304/9216。

将这两种与原失败的druidic chair组成独立诊断划分，在CUHK空闲GPU2/3进行真实双卡
训练，完整默认网络、8物体槽、每卡512环境、WM/Actor batch256、WM窗口8、想象32、
10次WM更新、5×4次Critic更新、BF16和编译均开启。仅将WM-only阶段设为0，并每次迭代
换场景和保存，尽早覆盖三类网络以及三种高需求资产。

连续3次迭代通过：所有rank的模型参数、归一化buffer、Adam状态及参数组逐字节一致，
所有数值有限；无CUDA OOM或物理缓冲溢出。第3次checkpoint时设备已用显存分别约
28.90与28.84 GiB（这是采样时刻的总占用，不是整个运行的峰值）。
随后从该checkpoint恢复并追加一次迭代到4，退出码0，一致性与有限值检查继续通过。

新增测试先复现密集凸块被过度扩容，以及Replay此前未拒绝Warp溢出标记的问题，再验证
修复。原有与本次新增测试共179项通过；测试时同工作区其他任务新增的24项也一并通过。

诊断代码只同步到服务器 `logs/cuhk_oom_visit27_20261027/source/`，服务器主项目保持
原提交与原有依赖配置。本地同名日志目录保存容量扫描、原训练报错、对照实验与审计JSON。
测试没有替正式任务排除任何训练椅子，也未重新启动长训练。

## 重启注意

同步本地修复后重新启动。建议训练JSON显式加入 `save_interval: 200`、`log_every: 10`，
缩短首次可恢复checkpoint的等待时间；修改文件不会作用于已运行的进程。保留原失败
运行目录，用新的run-dir启动。三种高需求资产的短训通过不保证任意未来姿态都不溢出，
长训练仍需监控；遇到明确容量溢出应增加相关容量，并相应减少环境数控制显存。
